01 The core idea

What Exactly Is Agent Programming?

Agent programming is the practice of building software agents that can pursue goals by reasoning about a situation, choosing actions, using tools, observing results, and adapting their next steps.

An agent might use a language model as its reasoning engine, conventional code for precise operations, databases for information, and APIs to interact with the outside world.

The important distinction is that the programmer defines the goal, capabilities, and constraints, while the agent determines some of the steps needed to reach the goal.

Three approaches to the same problem

Imagine you want to identify Db2 tablespaces that are running out of space.

APPROACH A

Traditional programming

Connect to Db2, execute a monitoring query, retrieve utilization, compare it against a threshold, and print warnings. The program follows the workflow you designed. To investigate why a tablespace is filling up, you must program the additional logic.

APPROACH B

An LLM answering a question

You ask, “Why is tablespace TS2 filling up?” An LLM might explain possible causes, but without relevant database evidence it cannot reliably determine the actual cause. Even with access, a simple tool-calling chatbot might stop after one query.

APPROACH C

An agent

You give it a goal: determine why TS2 is filling up, identify the tables responsible, estimate when it might run out of space, and recommend the safest corrective action. It chooses investigative steps based on what it discovers.

The agent might decide to:

  1. Retrieve current utilizationEstablish how much space the tablespace is using now.
  2. Examine historical growthCompare current measurements with earlier observations.
  3. Identify the tables responsibleFind the largest occupants and compare their growth rates.
  4. Investigate possible causesCheck whether growth appears associated with particular workloads.
  5. Estimate and evaluateProject when the tablespace might become full and assess potential remedies.
  6. Check the evidence and reportExplain the findings, assumptions, uncertainties, and recommended action.

If a query fails, the agent can try an alternative. If the initial evidence is insufficient, it can investigate further.

You didn't explicitly program that exact sequence of investigative steps. You built a system capable of choosing them within the boundaries you established.

The essential difference

Traditional software follows a workflow you designed. An agent can choose and adapt parts of its workflow in response to what it discovers.

One important qualification: an agent does not necessarily discover the correct answer or genuinely understand the system it investigates. Its reasoning can be wrong, and its actions must be constrained and verified.

02 The foundations

What Is the Underlying Science?

I find it useful to think of agent programming as the intersection of five disciplines.

Large language modelsInterpret goals, reason about context, and propose actions.
Planning and searchBreak goals into smaller objectives and select possible action sequences.
Control theoryObserve a system, act on it, measure the response, and adjust.
Software engineeringProvide reliable tools, APIs, execution environments, and explicit constraints.
Decision theoryEvaluate alternatives, uncertainty, costs, and potential consequences.

These disciplines existed before today's LLM-based agents. The recent development is the ability to combine flexible language-based reasoning with executable software tools and iterative feedback.

A real system also needs a safe way to stop or ask for help when it cannot proceed reliably.

The agent doesn't necessarily need a complex neural network for every part of this process.

For example, the LLM might decide which database query to execute, while ordinary Python code calculates growth rates and projects exhaustion dates.

An important engineering principle

Use probabilistic intelligence to decide what to investigate; use deterministic software wherever correctness can be established through precise computation.

03 The motivation

Why Is Agent Programming Needed?

Because many real-world problems cannot be completely specified in advance.

Imagine writing traditional software to investigate every possible reason for a database performance regression. You would need to anticipate:

  • Changes in data distribution.
  • Missing or outdated statistics.
  • New access plans.
  • Different query structures.
  • Unexpected interactions between workloads.
  • Hardware and memory constraints.
  • Unusual combinations of these conditions.

The number of possible combinations becomes enormous.

An agent offers a different approach: give it a collection of reliable tools and let it choose which investigations are relevant to the observed situation.

This is especially valuable when a task requires several rounds of investigation and the next step depends on the previous result.

However, agents are not always necessary. If a workflow is completely predictable, inexpensive, and well understood, a conventional program is often faster, cheaper, and more reliable.

The sweet spot

The sweet spot for agents is a problem with a clear objective but an unpredictable path toward the answer.

04 Beyond the usual examples

Five Unusual Applications

Customer-service chatbots, coding assistants, and travel planners are easy to imagine. The more interesting question is what happens when we give agents goals that require investigation, connecting evidence, and deciding what to do next.

Here are five possibilities to stretch the imagination—from discovering unexpected experiments to finding early disease signals and identifying gaps in scientific knowledge. Each begins with a “sweet spot” prompt: a goal broad enough to require investigation, but bounded by a clear outcome.

01

The Scientific Agent That Discovers Experiments Humans Wouldn't Think to Perform

Field: Molecular biology, biophysics, drug discovery

Imagine an agent investigating why certain cancer cells become resistant to a particular treatment. It could connect findings across papers, molecular pathways, experimental datasets, and competing hypotheses—then propose experiments that distinguish between explanations researchers may not have considered.

The intriguing possibility: An agent that doesn't just analyze existing results, but helps discover which experiment should happen next.

Sweet spot prompt“Investigate why these cancer cells may be developing resistance to this treatment. Review the available evidence and competing mechanisms, identify the most important uncertainties, and propose a ranked set of experiments that could distinguish between the hypotheses. Explain what each experiment would reveal, what result would challenge your hypothesis, and what evidence is still missing.”
02

The Agent That Reconstructs the Hidden Electrical Logic of the Brain

Field: Neuroscience, computational biology, dynamical systems

Imagine asking why a particular neural circuit transitioned from one activity pattern to another. An agent could examine neural recordings, timing, connectivity, and computational models to compare possible explanations for the transition—and suggest which measurements might help separate them.

The intriguing possibility: Treating brain activity not as a static picture, but as a changing electrical and dynamical system whose behavior can be investigated.

Sweet spot prompt“Analyze these neural activity recordings and the available information about the circuit. Identify when the activity pattern changes, compare plausible mechanisms that could explain the transition, and propose analyses or experiments that could distinguish them. Separate observations from hypotheses and state what the data cannot establish.”
03

The Agent That Finds the Earliest Detectable Signs of a Future Disease

Field: Preventive medicine, longitudinal data science, causal inference

Many diseases develop over years before they become clinically obvious. Given appropriately authorized, de-identified longitudinal health datasets, a research agent could look for combinations of subtle changes that tend to appear before diagnosis—and test whether those signals generalize beyond the data in which they were found.

The intriguing possibility: Looking for patterns that precede disease, rather than waiting for the disease to become obvious. Such patterns would be research signals, not diagnoses or proof of causation.

Sweet spot prompt“Using these authorized, de-identified longitudinal datasets, investigate which combinations of changes may precede the clinical onset of this disease by several years. Check data quality and potential confounders, test whether candidate signals generalize to separate cohorts, and distinguish predictive association from causal evidence. Do not present a research signal as an individual diagnosis.”
04

The Digital Ecosystem That Investigates Its Own Failures Before Humans Notice Them

Field: Complex systems, autonomous infrastructure, reliability engineering

Imagine an agent responsible for the reliability of a large computing environment containing databases, applications, network services, operating systems, data pipelines, AI models, and storage systems. Its job is not simply to alert an administrator when a component fails. It continuously looks for emerging failure patterns, connects clues across systems, estimates possible consequences, and recommends interventions before a small problem becomes an incident.

The intriguing possibility: An entire digital environment that investigates its own warning signs—while keeping risky changes behind explicit safeguards and approval.

Sweet spot prompt“Continuously examine the available telemetry, logs, dependencies, and recent changes across this environment. Detect emerging failure patterns, identify likely causes with supporting evidence, estimate potential consequences, and recommend the safest next diagnostic step or intervention. Do not make high-impact changes without the required authorization.”
05

The Agent That Discovers What Scientific Knowledge Is Missing

Field: Knowledge representation, philosophy of science, automated research

Scientific literature contains findings, assumptions, unresolved contradictions, and questions that fall between established research areas. An agent could map claims and the evidence supporting them, find where explanations depend on untested assumptions, and identify gaps that could be turned into tractable research questions.

The intriguing possibility: Not just finding answers in the scientific record, but helping researchers see which important questions the record still cannot answer.

Sweet spot prompt“Map the major claims, evidence, and open questions in this research area. Identify contradictions, unsupported assumptions, and connections between subfields that may reveal a knowledge gap. For each candidate gap, explain why it matters, what evidence would help resolve it, and how to test whether the gap is genuinely unresolved rather than simply missing from this collection of sources.”

These are illustrative possibilities, not claims that a fully reliable implementation already exists. Each would depend on suitable data, tools, evaluation, and carefully defined permissions.

05 The engineering reality

Agents Are a Design Choice, Not a Destination

Agent programming does not make conventional software obsolete. Agents can choose the wrong action, misinterpret evidence, repeat unproductive steps, or produce a confident answer that is not supported by the data.

They also introduce costs: additional model calls, latency, complexity, and a need to evaluate intermediate steps. For consequential actions, permissions, verification, and human approval may be essential.

The goal is not to make every program autonomous. It is to build systems that can investigate situations where the best next step depends on what they discover—while keeping the execution reliable, observable, and bounded.

THE BIG IDEA

From Executing Instructions to Pursuing Goals

Agent programming changes the relationship between a programmer and a workflow. Instead of specifying every step in advance, we define a goal, equip a system with useful tools, establish boundaries, and allow it to choose some of the steps based on evidence and feedback.

The promise isn't that software suddenly becomes infallible or human. It's that software can take on more of the investigative work required to solve problems whose paths cannot be fully scripted in advance.
